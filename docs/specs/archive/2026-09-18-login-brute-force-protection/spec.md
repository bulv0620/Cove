# 登录暴力破解防护

## 背景与问题

当前 `POST /api/auth/login` 会对存在和不存在的用户名执行 Argon2id 校验，并统一返回“用户名或密码错误”，能够降低用户名枚举和离线破解风险；但接口没有按来源 IP 或用户名限制尝试频率，也不记录登录成功、失败和受限事件。攻击者可以持续或并发提交密码猜测，并借助昂贵的 Argon2id 校验消耗 Server 资源。

本 Spec 为本地账号登录增加服务端双维度限流、递增冷却、统一 429 契约和安全审计。本文描述计划行为；在状态变为 `Approved` 或 `In Progress` 前不得实施。

## 目标

- 同时按可信来源 IP 和规范化用户名约束登录失败，降低单源和分布式密码猜测的速度。
- 冷却时间随持续失败递增，并设置上限和自然恢复路径，避免永久锁定。
- 所有登录限流使用不泄露账号是否存在或触发维度的统一 429 响应。
- 记录可追踪且不含密码、令牌或原始未知用户名的登录安全审计。
- 在正常登录、用户名枚举防护和现有会话语义上保持兼容。

## 非目标

- CAPTCHA、第三方风控、设备指纹、MFA、IP 黑名单或地理位置判断。
- 保护非登录 API、修改 JWT 有效期、密码规则或首次登录强制改密规则。
- 自动封禁账号、永久锁定、管理员手工解锁界面或安全告警通知。
- 由 Cove 自动配置外部反向代理、WAF、HTTPS 或防火墙。
- 将本次限流能力描述为能够阻止所有分布式低频攻击。

## 用户场景

### 偶发输错密码

用户在阈值以内输错密码时收到与当前一致的通用凭据错误；输入正确密码后正常登录，用户名维度的失败状态被清除。

### 针对单个账号持续猜测

同一用户名达到失败阈值后进入短暂冷却。冷却期内无论密码是否正确，Server 都不执行用户查询或 Argon2id 校验，而是返回统一 429 和剩余等待时间。冷却结束后再次验证失败会提高下一级冷却时间，直到上限；安静期后状态自然重置。

### 单一来源轮换用户名

同一来源 IP 在窗口内对多个用户名持续失败时，IP 维度独立进入冷却。更换用户名不能绕过该限制。

### 反向代理部署

未配置可信代理时，Server 只使用直接连接地址并忽略客户端提供的转发头。维护者显式配置可信代理 CIDR 后，Server 才从受信任代理链解析真实客户端地址。

## 功能需求

- `AUTH-RL-FR-001`：登录限流必须同时维护用户名和来源 IP 两个独立维度。用户名键使用与登录输入一致的 ASCII 用户名规则进行 `trim + lowercase` 规范化；IPv4 使用规范化单地址，IPv6 使用 `/64` 前缀，防止通过同一 IPv6 网段轮换地址绕过。存在与不存在的用户名必须经过相同的用户名限流流程。
- `AUTH-RL-FR-002`：默认策略必须使用 10 分钟失败窗口，用户名阈值为 5 次、IP 阈值为 20 次。达到阈值的那次已完成校验的失败请求仍返回统一 401，并开始 30 秒冷却；冷却结束后的下一次实际校验如果仍失败，冷却时间按 `30 × 2^level` 秒递增，最多 15 分钟。连续 30 分钟没有实际校验失败后，该维度恢复初始状态。
- `AUTH-RL-FR-003`：处理登录请求前必须原子检查两个维度并预留一次有期限的密码校验额度；任一维度仍在冷却期或可用校验额度已被并发请求占满时，不查询用户、不执行 Argon2id、不签发 JWT，并按冷却截止时间或最早预留到期时间返回 429。冷却期间收到的请求不得延长或提高冷却级别。完成校验后必须原子结算或释放预留，请求中断后预留必须自动过期，不能通过竞态超出阈值后继续批量执行密码校验。
- `AUTH-RL-FR-004`：密码校验成功必须清除该规范化用户名的失败和冷却状态，并正常更新最后登录时间、签发 JWT；成功不得清除 IP 维度中由其他用户名产生的失败状态。IP 和用户名状态均在安静期后自然重置，维护者不需要手工解锁。
- `AUTH-RL-FR-005`：所有受限登录必须返回 HTTP 429、`Retry-After: <seconds>` 响应头，以及 JSON `{ "statusCode": 429, "error": "Too Many Requests", "code": "AUTH_RATE_LIMITED", "message": "Too many login attempts. Try again later.", "retryAfterSeconds": <seconds> }`。`retryAfterSeconds` 和响应头必须为相同的向上取整正整数；响应不得说明 IP、用户名、账号存在性、失败次数或具体触发维度。
- `AUTH-RL-FR-006`：Web 登录页必须识别 `AUTH_RATE_LIMITED`，以中英文显示通用的稍后重试提示和剩余等待时间；等待期间可以阻止重复提交，倒计时结束后允许重试。401 仍显示现有通用凭据错误，429 不得被显示为服务器故障或清除现有登录 token。
- `AUTH-RL-FR-007`：Server 必须写入 `auth.login.success`、`auth.login.failure` 和 `auth.login.rate_limited` 审计事件。成功事件关联用户 ID；已知用户的失败可以关联用户 ID，未知用户名只能记录不可逆的键控指纹。审计必须记录结果、规范化来源 IP、时间以及安全所需的冷却摘要，不得记录密码、JWT、原始未知用户名、完整请求体或用于计算指纹的密钥。
- `AUTH-RL-FR-008`：每次实际密码校验成功或失败必须有一条对应审计。冷却期或并发校验额度饱和时的重复请求，只在每个触发维度的每段冷却或饱和窗口首次受限时记录 `auth.login.rate_limited`，其余请求只原子累加限流状态中的受限计数，避免审计写放大；后续状态转换或清理时将聚合计数写入审计摘要。
- `AUTH-RL-FR-009`：限流状态必须持久化到 MySQL，并通过数据库唯一键和事务/原子更新保证同一键的并发一致性；应用重启不能清除仍有效的冷却。状态键必须使用从 `JWT_SECRET` 以独立上下文标签派生的 HMAC-SHA-256，不保存原始用户名或原始 IP。超过保留期的失效状态必须可被有界批量清理。
- `AUTH-RL-FR-010`：默认忽略 `X-Forwarded-For`、`Forwarded` 等客户端转发头。只有直接连接地址命中维护者显式配置的可信代理 CIDR 时才按从右向左的可信链规则解析客户端 IP；配置非法时 Server 必须拒绝启动，且不得提供“信任所有代理”的生产默认值。
- `AUTH-RL-FR-011`：失败窗口、两个阈值、基础/最大冷却、安静重置时间、校验额度预留期限、状态保留期和可信代理 CIDR 必须由有界且启动时校验的 Server 配置提供，示例配置写明上述默认值；安全限流不得通过空值或零值静默关闭。限流存储或原子更新失败时登录必须失败且不得签发 token。

## 非功能需求

- `AUTH-RL-NFR-001`：阈值前的未知用户仍必须执行现有 dummy Argon2id 校验；401 与 429 的响应内容、时序分支和审计不得形成可实用的用户名存在性判断。
- `AUTH-RL-NFR-002`：429 快速拒绝路径不得执行 Argon2id；限流检查和计数更新必须有界，不能随历史请求数线性扫描。清理任务必须分批执行，不能阻塞登录接口或无界增长数据库。
- `AUTH-RL-NFR-003`：登录限流、成功清理和审计在并发及多进程访问同一数据库时必须保持一致；虽然当前部署为单 Server，设计不得依赖单进程内存锁保证安全性。
- `AUTH-RL-NFR-004`：密码、token、请求体、HMAC 派生密钥和未批准的原始/HMAC 值不得进入普通应用日志、错误响应或审计 metadata；仅允许限流表保存完整 `keyHash`，审计保存经独立上下文派生且截断的未知用户名指纹。测试使用隔离凭据并扫描日志、响应、限流状态和审计记录。
- `AUTH-RL-NFR-005`：数据库迁移必须支持现有数据原地升级和兼容回滚说明；旧版本回滚时新增限流表可以保留但不会被旧代码读取，不得改变已有用户、密码凭据或会话数据。

## 验收条件

- `AUTH-RL-AC-001`（FR-001/002/003/004）：使用可控时钟验证用户名前 4 次失败为 401，第 5 次失败为 401 并开始 30 秒冷却，冷却内请求均为 429 且不调用用户查询/Argon2id；冷却结束后再次失败触发 60 秒，持续失败最终封顶 15 分钟。30 分钟安静期后恢复初始状态，正确密码清除用户名状态。
- `AUTH-RL-AC-002`（FR-001/002/003）：同一 IP 轮换至少 20 个用户名触发 IP 冷却；同一用户名来自多个 IP 仍触发用户名冷却；大小写变体、首尾空白和同一 IPv6 `/64` 内轮换不能绕过。一个维度成功或切换用户名不得错误清除另一维度状态。
- `AUTH-RL-AC-003`（FR-003/005/006）：受限请求返回完全一致的 429 body 和一致的 `Retry-After`/`retryAfterSeconds`，不泄露触发维度或账号存在性；中英文登录页显示等待提示并在倒计时后恢复提交，401、网络失败和 429 保持可区分的用户体验。
- `AUTH-RL-AC-004`（FR-007/008、NFR-004）：成功、实际失败和冷却首次受限生成正确审计结果；受限请求洪泛不会逐请求新增审计行，聚合计数可追踪。数据库、审计、日志及 HTTP 响应扫描确认不存在测试密码、JWT、原始未知用户名、HMAC 密钥或请求体。
- `AUTH-RL-AC-005`（FR-003/009/011、NFR-002/003）：并发测试在阈值边界同时发送请求，证明原子预留使阈值后的请求不再执行 Argon2id；两个 Server 进程共享 MySQL 时不能分别获得独立额度。正常完成会结算预留，中断请求的预留到期后可恢复额度。重启 Server 后冷却仍有效，过期记录由有界批次清理，存储故障不允许绕过并签发 token。
- `AUTH-RL-AC-006`（FR-010/011）：未配置可信代理时伪造转发头不改变限流 IP；配置明确的单层和多层可信代理后解析结果符合从右向左规则；来自非可信直连方的转发头被忽略，非法 CIDR 或越界参数使 Server 启动失败且错误不包含 secret。
- `AUTH-RL-AC-007`（FR-005、NFR-001）：对存在、禁用、不存在账号执行等量失败与受限请求，确认 401/429 状态和响应完全一致；在允许误差内检查快速拒绝路径没有因用户查询或 Argon2id 产生账号存在性差异。
- `AUTH-RL-AC-008`（NFR-005）：从现有数据库执行迁移后用户、凭据、角色、会话版本和审计数据不变，登录回归通过；保留新增表时旧应用可按记录方案回滚，重新升级后有效冷却状态行为明确。
