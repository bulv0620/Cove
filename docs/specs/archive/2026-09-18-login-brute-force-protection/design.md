# 技术设计

## 设计摘要

本文描述计划实现。登录入口在密码校验前调用持久化限流器，按用户名和客户端 IP 两个 HMAC 键原子判断是否处于冷却并预留校验额度；若冷却中或额度已满则立即返回统一 429。取得预留的请求继续沿用现有用户查询、dummy hash 和 Argon2id 验证，随后原子结算两个维度的结果与安全审计。

```text
POST /api/auth/login
  → 解析并规范化可信客户端 IP、用户名
  → MySQL 原子预检 USERNAME + IP 状态并预留校验额度
      ├─ 冷却中/额度已满 → 累加 blockedAttempts → 统一 429（无查询/Argon2）
      └─ 已取得短期预留 → 现有用户查询 + Argon2id/dummy hash
                           ├─ 失败 → 原子结算预留、增加两个维度 + 审计 → 401
                           └─ 成功 → 释放预留、清除用户名状态 + 审计 → JWT
```

## 组件与边界

- `AuthController` 只提取请求上下文、调用登录用例并返回 HTTP 契约；客户端 IP 解析位于可单测的 Server 基础设施组件。
- `AuthService` 保留认证编排，先调用 `LoginThrottleService.preflight`，完成现有密码验证后调用成功或失败转换。
- `LoginThrottleService` 负责键派生、策略计算、原子状态转换、清理和 429 剩余时间，不持有明文密码。
- `AuditService` 扩展为可显式写入 `SUCCESS`/`FAILURE`，认证模块复用同一审计入口。
- Web API 错误类型扩展稳定的 `code` 和 `retryAfterSeconds` 字段；登录页只根据 code 处理限流，不解析英文 message。

所有安全判断以 Server 和 MySQL 为准。前端倒计时只减少无意义重试，不构成安全边界。

## 数据模型

新增 `AuthLoginThrottle`（物理表建议 `auth_login_throttles`）：

| 字段                  | 说明                                        |
| --------------------- | ------------------------------------------- |
| `scopeType`           | `USERNAME` 或 `IP`，与 `keyHash` 组成唯一键 |
| `keyHash`             | HMAC-SHA-256 十六进制值，不保存原始键       |
| `failureCount`        | 当前失败窗口内完成密码校验的失败数          |
| `cooldownLevel`       | 超过阈值后的递增级别                        |
| `windowStartedAt`     | 当前失败窗口起点                            |
| `lastFailureAt`       | 最后一次实际校验失败时间                    |
| `cooldownUntil`       | 当前冷却截止时间；未冷却时为空              |
| `blockedAttempts`     | 当前冷却中被快速拒绝的聚合数量              |
| `limitedAuditAt`      | 当前冷却是否已产生首次受限审计              |
| `createdAt/updatedAt` | 生命周期与清理索引                          |

唯一键为 `(scopeType, keyHash)`，并对清理所需时间字段建立索引。状态不关联 `User` 外键：不存在用户名也必须得到相同行为，删除用户也不能破坏限流记录。

另新增短期校验预留表 `AuthLoginVerificationReservation`：包含随机 ID、用户名键、IP 键、创建时间和 `expiresAt`，并分别索引两个键与到期时间。预留不包含用户名、IP、密码或用户 ID。预留默认 30 秒到期；每次预检先忽略或清理已过期项，再将“已完成失败数 + 有效预留数”与阈值比较。这样只在短事务内分配额度，不会在 Argon2id 执行期间占用数据库事务或行锁。

HMAC 密钥通过 HKDF/HMAC 从 `JWT_SECRET` 和固定上下文 `cove/auth-login-throttle/v1` 派生，绝不直接复用 JWT 签名输入。JWT secret 轮换会使旧限流行不可寻址；这与轮换导致所有旧 JWT 失效一起作为计划内安全状态重置记录，旧行随后按保留期清理。

## 限流算法

用户名只允许既有 ASCII 字符集，限流键使用 `trim().toLowerCase()`；认证查询继续使用当前已定义的 trim 行为，不借本 Spec 改变账号匹配语义。IP 先解析为二进制地址：IPv4 映射地址归一为 IPv4，IPv4 使用 `/32`，IPv6 清零低 64 位后使用 `/64`。

默认策略：

| 参数           | 默认值  |
| -------------- | ------- |
| 失败窗口       | 10 分钟 |
| 用户名阈值     | 5       |
| IP 阈值        | 20      |
| 基础冷却       | 30 秒   |
| 最大冷却       | 15 分钟 |
| 无失败状态重置 | 30 分钟 |
| 校验额度预留   | 30 秒   |
| 失效状态保留   | 24 小时 |

首次达到阈值时 `cooldownLevel = 0`，`cooldownUntil = now + 30s`。冷却结束后的下一次真实校验仍失败时级别加一，冷却为 `min(30s × 2^level, 15m)`。冷却期间快速拒绝不改变 `failureCount`、`cooldownLevel`、`lastFailureAt` 或 `cooldownUntil`，只累加 `blockedAttempts` 并按审计规则标记首次受限。

预检必须在一个短事务中锁定或原子创建两个状态键，统计有效预留并插入本次预留，再基于同一个数据库/注入时钟计算决定。对同键的并发请求需要串行取得校验资格，不能让阈值边界后的并发都进入 Argon2。实现可以使用 Prisma transaction 加针对 MySQL 的条件更新/行锁，但不得只做“先读后写”的非原子流程，也不得把数据库事务跨越到密码哈希阶段。

完成密码校验后，以预留 ID 原子结算：失败时删除预留并同时更新 USERNAME 与 IP；成功时删除预留并只删除/重置 USERNAME 键。IP 状态保留到窗口或安静期结束，避免攻击者用一个已知密码反复清空 IP 额度。请求在结算前中断时，预留到期后自动恢复额度；到期清理必须幂等。事务或审计写入失败时不签发 token。数据库不可用时沿用安全失败方向返回通用服务错误，不降级为无限制登录。

## API 契约

受限响应固定为：

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 42
Content-Type: application/json

{
  "statusCode": 429,
  "error": "Too Many Requests",
  "code": "AUTH_RATE_LIMITED",
  "message": "Too many login attempts. Try again later.",
  "retryAfterSeconds": 42
}
```

剩余秒数以服务端截止时间减当前时间后向上取整，最小为 1。两个维度同时冷却时使用较晚截止时间；只有并发预留占满额度而尚未形成冷却时，使用相关有效预留中最早的到期时间。响应不向客户端返回维度或受限原因。达到阈值的那次密码错误仍返回现有 401，避免把账号状态差异带入当前响应；后续请求返回 429。

Web 的 `ApiError` 保留 HTTP status，并新增可选 `code` 与 `retryAfterSeconds`。登录页针对 code 显示本地化文案；倒计时以服务端值初始化，页面后台恢复时按绝对本地截止时间重新计算，不能每次 render 重置。

## 可信客户端 IP

新增 `AUTH_TRUSTED_PROXY_CIDRS`，默认空。为空时完全忽略转发头，以 TCP 直接连接地址为客户端 IP。配置后仅当直接对端在可信 CIDR 中，才解析标准 `Forwarded` 和兼容的 `X-Forwarded-For` 链；从右向左跳过受信任代理，选择第一个非可信地址。格式冲突、地址非法或链缺失时使用直接对端，不接受任意客户端声明。

配置支持明确的 IPv4/IPv6 CIDR 列表，不支持无约束的 `true`/`*`。代理拓扑变化必须同步配置，否则限流会按直接代理地址聚合；这属于安全的保守退化。实现需确保 Nest/Express 其他 `request.ip` 使用者与认证解析规则一致，避免审计和限流记录不同地址。

## 审计与可观测性

审计事件：

| action                    | result    | target/metadata                                            |
| ------------------------- | --------- | ---------------------------------------------------------- |
| `auth.login.success`      | `SUCCESS` | 用户 ID、IP；不记录限流键或 token                          |
| `auth.login.failure`      | `FAILURE` | 已知用户 ID 或未知用户名指纹、IP、开始冷却的维度及冷却秒数 |
| `auth.login.rate_limited` | `FAILURE` | 触发维度、冷却秒数、该段冷却的聚合受限数；不记录账号存在性 |

已知用户和未知用户名在响应上完全一致。未知输入使用从同一根密钥、独立审计上下文派生并截断的 HMAC 指纹，不能直接复制完整限流 `keyHash`；审计 metadata 不记录原始输入。为了避免 429 洪泛放大数据库，每个限流维度在每段冷却或并发预留饱和窗口只写一次首次受限事件，其余只累加状态。下一次真实状态转换或清理时补充最终聚合数；如果进程在此之前退出，持久化状态仍保留该计数供后续处理。

普通应用日志只允许输出 action、结果、请求关联 ID和不含键值的错误码。不得打印请求 body、密码、JWT、原始用户名、完整 HMAC 或派生材料。若未来提供审计查看界面，其权限与保留策略另行定义；本 Spec 只写入现有审计存储。

## 配置与清理

计划配置项包括失败窗口、用户名/IP 阈值、基础和最大冷却、安静重置、密码校验预留期限、保留期及可信代理 CIDR。时间配置使用明确的秒/小时后缀，解析后施加合理上下界，并要求最大冷却不小于基础冷却、重置期不短于失败窗口。预留期限必须覆盖正常 Argon2id 校验的合理上界，同时保持较短的中断恢复时间。非法值使 Server 启动失败，错误只指出变量名和规则。

每个登录状态转换可顺带触发低频、有上限的过期行删除；也可使用单实例无害的周期批次。多进程同时清理必须幂等。每批数量固定，按索引时间字段删除，不能全表加载；清理失败不删除有效状态，并按限频方式记录运维错误。

## 迁移与兼容性

新增表和枚举/字符串字段，不修改 `users`、`password_credentials`、`audit_logs` 既有数据。升级先执行 Prisma migration，再启动新应用。新代码首次请求时按需创建状态，不要求回填。

应用回滚时旧代码忽略新增表，既有登录恢复旧行为；回滚期间没有应用级暴力破解防护，因此应保留外部访问限制。重新升级后 24 小时内的状态仍可能生效；维护者如因灾难恢复必须清理，应通过明确、带备份的数据库操作完成，不能加入日常“解除锁定”按钮。

## 安全分析

- 双维度限制分别约束单 IP 轮换账号和多 IP 集中攻击账号；仍无法彻底阻止大量来源的低频分散攻击。
- 冷却前检查避免 Argon2 资源消耗；dummy hash 保留阈值前的枚举防护。
- 用户名冷却可能被用于短时拒绝特定账号。冷却上限、禁止受限请求延长、安静重置和不设永久锁定限制影响；MFA/验证码不在本轮范围。
- IP 阈值可能影响 NAT 后多个用户。默认 IP 阈值高于用户名阈值，并允许在有界范围调整；成功登录不会清 IP 状态，以免形成简单绕过。
- 代理头仅在可信直接对端启用，防止攻击者伪造 IP 轮换限流键。
- HMAC 状态键降低数据库泄露后枚举未知用户名/IP 的能力；审计仍保存安全调查所需的规范化 IP，沿用现有审计数据边界。

## 验证策略

- 使用注入时钟和 Argon2/user lookup spy 做限流状态机单元测试，覆盖阈值、指数冷却、封顶、安静重置、成功清理及预留到期。
- 使用真实 MySQL 做并发集成测试，覆盖唯一键竞争、额度预留/结算、请求中断、事务边界、双进程共享额度、重启保留和批量清理。
- 做 API 契约测试，精确检查 401/429 body、header、秒数取整及存在/不存在/禁用用户的一致性。
- 做可信代理解析表驱动测试，覆盖 IPv4、IPv4-mapped IPv6、IPv6 `/64`、单/多层代理、伪造头和非法配置。
- 做 Web 交互测试，覆盖中英文提示、倒计时、后台恢复、401 与网络失败；不需要用真实等待，使用可控时钟。
- 用唯一 canary 密码和 token 扫描日志、HTTP 响应、审计 metadata 和限流表。

## 备选方案

- 仅使用 Nest 通用 IP 限流：实现简单，但无法限制多 IP 对单账号的攻击，也不能完整表达递增冷却。
- 只在内存保存状态：减少数据库写入，但重启和多进程可绕过，不符合本 Spec。
- 永久账号锁定：阻断力强，但容易被利用为管理员账号拒绝服务，需要额外解锁流程，本轮不采用。
- CAPTCHA：可作为未来异常挑战，但不能替代服务端限流，且会增加可用性、隐私和外部依赖成本。
